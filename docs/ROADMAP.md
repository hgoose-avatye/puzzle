# 개발·폴리싱 계획 (2026-10-30 개정)

[경쟁작 비교](competitor-comparison.md), [현황](STATUS.md), [폴리싱 목록](POLISH.md)을 바탕으로 한 실행 계획이다. 2026-10-30에 사용자 결정에 맞춰 고쳤다.

## 결정 사항 (2026-10-30)

| 항목 | 결정 |
|---|---|
| 개발 순서 | P0 규칙 안정화 → P1 방향 인식·조작 UX → P2 첫 10분 경험 → P3 게임 화면 완성 → P4 아트·레벨 폴리싱 |
| 튜토리얼 형식 | **손가락 안내 + 실제 조작**, 그림 카드는 최소한. 카드를 먼저 읽히고 플레이시키는 방식은 쓰지 않는다 |
| 튜토리얼 시작 시점 | **방향 인식 문제(P1)가 해결된 뒤.** 방향을 모르는 문제를 튜토리얼로 덮지 않는다 |
| 특수 요소 교체 | **확정하지 않는다.** 가족 줄·번호 문은 요소마다 테스트 레벨 3~5개로 "기존 규칙과 다른 판단·재미"를 확인한 뒤 결정 |
| 출시 레벨 수 | **확정하지 않는다.** 먼저 30레벨(수작업 학습 레벨 12 + 난이도를 검증한 일반 레벨 18)을 높은 완성도로 만들고, 그 뒤 확장 여부를 판단 |
| 기존 생성 레벨 | 180개(`src/curve/levels.json`)는 **삭제하지 않고 보존** |
| 검증 | **개발자 자체 플레이**와 **실제 이용자 테스트**를 구분한다. 출시 전에 목표 이용자(40~60대)가 설명 없이 첫 10분을 플레이하는 테스트를 둔다 |

## 검증 방법 용어

| 이름 | 하는 사람 | 무엇을 확인 |
|---|---|---|
| **자동 테스트** | 코드(`npm test`) | 규칙, 풀이 가능성, 불변 조건 |
| **헤드리스 검증** | 스크립트(실제 브라우저, 화면 없이) | 실제 게임 흐름, 스크린샷 |
| **스크린샷 검증** | 사람이 스크린샷을 보고 판단 | 보이는지, 읽히는지 |
| **자체 플레이** | 개발자·기획자 | 체감, 버그. 이미 규칙을 아는 사람이라 "처음 보는 사람"의 이해도는 판단할 수 없다 |
| **이용자 테스트** | 목표 이용자, 설명 없이 | 이해도, 실수, 재미. 관찰하고 개입하지 않는다 |

## P0. 게임 규칙 안정화

**목표**: 동시 이동, 충돌, 자동 대기·재개, 하트 판정이 어떤 순서로 눌러도 틀리지 않는다.

**선행 조건**: 없음(지금 시작 가능).

**작업 항목**: 아래 [P0 작업 계획](#p0-작업-계획) 참고.

**완료 기준**
- 규칙 명세서 한 장이 있고, 코드가 그 명세와 일치한다.
- 실제 게임 흐름(탭 → 논리 판정 → 이동·대기 → 상자 → 클리어·실패)을 묶은 자동 테스트가 180레벨 × 무작위 연타에서 불변 조건을 모두 지킨다(겹침 없음, 하트는 정해진 경우에만 줄어듦, 클리어는 모든 동물이 나간 뒤에만).
- 헤드리스 검증 스크립트가 저장소에 있고 통과한다.

**검증 방법**: 자동 테스트, 헤드리스 검증, 자체 플레이 체크리스트(연타·두 손가락·재시작).

## P1. 방향 인식·조작 UX

**목표**: 1칸 동물이 어느 쪽으로 가는지 바로 보이고, 누른 결과가 예측 가능하다.

**선행 조건**: P0의 규칙 명세(무엇이 실수이고 하트를 잃는지)가 확정되어 있어야 한다.

**작업 항목**: 아래 [P1 작업 계획](#p1-작업-계획) 참고.

**완료 기준**
- 1칸 동물 방향 표시가 네 방향과 가려지는 경우(폴리싱 F8) 모두에서 스크린샷으로 읽힌다.
- 누를 때 선택 피드백이 있고, 달리는·기다리는 동물을 눌러도 반응이 있다.
- 자체 플레이로 레벨 1~30에서 방향을 잘못 읽어 하트를 잃는 일이 없다.

**검증 방법**: 스크린샷 검증(네 방향 × 가려짐 유무), 자체 플레이. 이용자 이해도는 P2의 이용자 테스트에서 함께 확인한다.

## P2. 첫 10분 경험

**목표**: 처음 하는 사람이 설명 없이 규칙과 우리 게임만의 재미를 익힌다.

**선행 조건**: P1 완료.

**작업 항목**
1. 레벨 데이터 덮어쓰기 구조: 손으로 만든 레벨이 생성 레벨보다 우선. 생성 레벨 180개는 그대로 보존
2. 수작업 학습 레벨 12개. 안(案):
   - 1: 동물 한 마리만 있고, 손가락이 가리키면 직접 탭
   - 2: 막힌 동물(누르면 흔들리고 하트가 준다는 것을 안전하게 경험)
   - 3: 앞 동물을 먼저 보내야 하는 순서
   - 4: **여러 마리를 연속으로 누르면 앞 동물이 지나간 뒤 자동으로 따라감**(우리 차별점, 꼭 보여 줌)
   - 5: 1칸 동물의 방향 표시
   - 6~12: 화살표, 하트, 상자, 긴 동물을 하나씩, 그리고 섞어 보기
3. 손가락 안내(실제 조작) + 최소한의 그림 카드
4. 일반 레벨 18개: 생성 레벨 중에서 고르고, 자체 플레이로 난이도를 검증해 다듬음

**완료 기준**: 자체 플레이로 30레벨이 막힘 없이 흐르고, **이용자 테스트 1차**(목표 이용자 3~5명, 설명 없이 첫 10분)에서 레벨 1~12를 도움 없이 깬다.

**검증 방법**: 자체 플레이, 이용자 테스트(관찰 기록: 어디서 멈췄는지, 하트를 왜 잃었는지).

## P3. 게임 화면 완성

**목표**: 출시에 필요한 화면이 모두 있다.

**선행 조건**: P2의 튜토리얼 흐름이 정해져야 메인·설정의 "튜토리얼 다시 보기"를 연결할 수 있다.

**작업 항목**: 메인 화면, 일시정지·설정(효과음·볼륨·진동), 성공·실패 화면 개선, 효과음 볼륨 조정, 햅틱, 로딩, 정보·라이선스. 광고가 필요한 실패 후 이어 하기와 힌트 정책은 SDK가 정해진 뒤.

**완료 기준**: 화면 목록(STATUS 3)의 1~3순위가 모두 있고, 실제 기기에서 효과음·진동이 확인된다.

**검증 방법**: 스크린샷 검증, 실제 기기 자체 플레이.

## P4. 아트·레벨 폴리싱

**목표**: 레퍼런스 수준의 화면과 검증된 레벨 구성.

**선행 조건**: 에셋 확보 방식 결정, P2의 30레벨 완성.

**작업 항목**
- 아트: 소품·건물, 물·빛, 캐릭터 연출(선택 시 빛남, 막힘 시 고개 젓기)
- 레벨: 30레벨 난이도 재검증, 이후 확장 여부 판단
- **특수 요소 검증**: 가족 줄·번호 문 테스트 레벨(아래 [특수 요소 검증 계획](#특수-요소-검증-계획))로 판단 후 교체 여부 결정
- 폴리싱 목록의 나머지 항목

**완료 기준**: 레퍼런스 03·04·08과 나란히 놓았을 때 같은 게임으로 보이고, **이용자 테스트 2차**(출시 후보 빌드, 설명 없이 첫 10분)에서 1차의 문제가 다시 나오지 않는다.

**검증 방법**: 스크린샷 검증, 이용자 테스트 2차.

## 특수 요소 검증 계획

교체 여부를 정하기 전에, 요소마다 테스트 레벨 3~5개로 "기존 규칙에 없는 판단"이 생기는지 본다. P4에서 진행하며 생성 레벨 180개와 기존 요소는 그대로 둔다.

| 요소 | 규칙(안) | 기존 규칙과 다른 점이 있어야 하는 부분 | 테스트 레벨(안) | 판단 기준 |
|---|---|---|---|---|
| **가족 줄** | 엄마 동물 뒤에 아기들이 줄지어 있고, 엄마를 누르면 **아기들도 한 번에 함께** 나간다. 아기는 따로 누를 수 없다 | 자동 대기·재개는 "여러 번 누른 것을 순서대로 처리"한다. 가족 줄은 **한 번 누르면 여러 마리가 나가서 판이 크게 열리는** 것이 다르다. 그 대신 줄 전체가 지나갈 길이 비어 있어야 한다 | ① 가족 하나만 ② 줄이 길어서 길을 오래 막는 경우 ③ 줄이 꺾이는 길 ④ 막판에 가족이 나가며 한꺼번에 열리는 판 | 자체 플레이에서 "이 줄을 언제 보낼까"라는 새 판단이 생기는가, 막판 해소감이 있는가 |
| **번호 문** | 출구 문에 번호가 있고 1번 문부터 차례로 열린다. 아직 안 열린 문으로 가는 동물은 막힘 | 열쇠·잠금은 "특정 동물이 먼저"였다. 번호 문은 **판 전체의 나가는 순서를 문이 정해서**, 여러 동물을 묶어 생각하게 한다 | ① 문 2개 ② 문 3개, 같은 번호 문이 여러 개 ③ 화살표로 다른 문으로 돌려 보내기 | 열쇠·잠금보다 계획이 더 필요하고, 읽기는 쉬운가(40~60대) |

판단이 서면 폭탄·자는 동물·열쇠를 교체할지, 함께 둘지, 그대로 둘지 결정한다.
