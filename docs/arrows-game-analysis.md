# Arrows 게임 로직 분석

분석 대상: `/Applications/Arrows.app` (iOS 앱, `com.ecffri.arrows`, v0.23.1, 빌드 4)
목적: 레벨 생성기를 만들기 위해 규칙과 난이도 구조를 파악한다. 디자인·에셋은 새로 만들 예정이라 이 문서에서는 다루지 않는다.

각 항목에 근거 수준을 표시했다.

- **[검증]**: 레벨 데이터 4,852개로 직접 확인했다.
- **[추정]**: 클래스 이름 등 간접 증거로 추정했다. 확정이 아니다.
- **[미확인]**: 알 수 없다.

---

## 1. 분석 범위와 한계

- 앱은 APK가 아니라 **iOS 빌드**다. Mac에서 iOS 앱으로 설치된 상태다.
- 실행 파일(`Arrows`, `UnityFramework`)은 **FairPlay로 암호화**돼 있다(`cryptid 1`). 복호화하지 않았다. 그래서 IL2CPP로 컴파일된 **게임 로직의 실제 코드(생성 알고리즘, 난이도 수식)는 읽지 못했다.**
- 읽은 것은 다음 세 가지다.
  1. `global-metadata.dat`의 문자열(클래스·메서드·필드 이름)
  2. 암호화되지 않은 Addressables 번들의 레벨 데이터
  3. `Info.plist`, 프레임워크 목록
- 따라서 **규칙은 레벨 데이터로 검증**했고, **난이도 배정 방식은 이름과 통계로 추정**했다.

### 생성기에 중요한 시사점

- 서버가 `LevelFinished(level, arrows, profile)`과 `ReportAttempt`를 기록한다. 즉 **플레이 결과를 서버로 모아 레벨 난이도 보정에 쓰는 구조**일 가능성이 있다 **[추정]**.
- 레벨은 앱에 번들된 **고정 데이터**다. 런타임에 생성하지 않고 오프라인 도구로 만든 뒤 배포한 것으로 보인다.

## 3. 핵심 규칙 **[검증]**

레벨 4,852개를 이 규칙으로 풀어 보았고, **전부 풀렸다.** 규칙이 틀렸다면 이렇게 나오기 어렵다.

1. 격자(XSize × YSize) 위에 **화살표**가 여러 개 있다.
2. 화살표는 **경로**다. 인접한 셀들을 잇는 꺾인 선이고, 한쪽 끝이 **머리**다.
3. 머리 방향은 **마지막 구간의 진행 방향**이다. 머리에서 그 방향으로 격자 밖까지 직선을 그을 수 있다.
4. 그 직선(경로 위에 놓인 모든 셀)에 **다른 화살표의 셀이 하나도 없으면** 그 화살표는 나갈 수 있다.
5. 화살표를 탭하면 머리 방향으로 빠져나가 사라진다. 막혀 있으면 실패다(`Mistake`, 하트 감소 **[추정]**).
6. **모든 화살표를 없애면 클리어**다.
7. 화살표끼리 셀이 겹치는 레벨은 없다.

### 풀이 가능성의 성질

- 한 화살표가 사라지면 다른 화살표가 막히는 일은 없다. 그래서 **나갈 수 있는 화살표를 아무거나 먼저 빼도** 풀이 가능성은 변하지 않는다.
- 따라서 풀이 가능 판정은 **그리디 한 번**이면 된다. 나갈 수 있는 화살표가 없는 상태에서 멈추면 풀 수 없는 레벨이다.
- 생성기에서 "반드시 풀리는 레벨"을 보장하기 쉬운 이유다. 막힘 관계가 **비순환(DAG)** 이면 된다.

### 대각선 **[검증]**

- 버킷 08, ThunderRush 레벨은 **대각선 구간**을 가진다(8방향 이동).
- 대각선 레벨에서도 규칙은 같고, 머리 방향이 대각선일 수 있다. 메타데이터의 `Bending (Diagonals)`, `DiagonalLevelFrequency`와 맞는다.

## 4. 레벨 데이터 포맷 **[검증]**

번들 3개: `levels-main`(3,983개), `levels-daily`(646개), `levels-thunderrush`(223개). 각 레벨은 ScriptableObject 하나다.

```
Data:
  XSize, YSize      : 격자 크기
  Arrows[]          : 화살표 목록
    CompactIndices[]: 경로의 꼭짓점(머리, 꺾이는 점들, 꼬리)만 담은 셀 인덱스
  SpecialArrowId    : 특수 화살표 ID (-1은 319개 레벨, 나머지는 양수 값 예: 27, 28, 31, 41)
  _staticFlags      : 비트 플래그 (0, 1, 1024, 8, 64, 16, 4, 128, 20, 129, 161)
```

- 셀 인덱스는 `index = y * XSize + x`다.
- `CompactIndices`는 **꼭짓점만** 저장한다. 인접한 두 값 사이는 직선(가로, 세로, 또는 대각선)이다.
  - 예: 45×45에서 `[829, 874, 872]` → (4,18) → (4,19) → (2,19)
- **첫 번째 값이 머리**다. 이 방향이어야 4,852개가 전부 풀린다. 반대 방향으로 해석하면 4,849개가 풀리지 않는다.
- `SpecialArrowId`, `_staticFlags`의 의미는 **[미확인]** 이다. `_staticFlags`는 모양 레벨, 대각선 레벨, 이벤트 레벨 같은 구분으로 보이지만 확인하지 못했다.

### 레벨 이름 규칙 **[검증]** (의미는 [추정])

```
07-02_[34x36]_[115]_[Basic]
 │  │    │      │     └ 생성 스타일 태그 (여러 개 가능)
 │  │    │      └ 화살표 수
 │  │    └ 격자 크기
 │  └ 두 번째 숫자
 └ 첫 번째 숫자
```

- 첫 번째 숫자(04, 05, 06, 07, 08, 10)는 **생성 프로필 그룹**으로 보인다. 그룹마다 격자 크기, 밀도, 대각선 사용 여부가 뚜렷하게 다르다(5절).
- 두 번째 숫자는 **그룹 안의 프리셋 번호**로 보인다. 숫자가 클수록 어렵거나 쉬운 단조 관계가 없다(6절).
- 이름만 있는 모양 레벨도 있다: `Star`, `Cloud`, `Ghost`, `Heartv2`, `Moon`, `knight`, `piggy`, `OG_Level*`.
  - 이건 **일러스트 모양에 맞춰 배치한 특수 레벨**이다.

### 관찰

- 격자가 모두 **크다(25~48칸)**. 화면에 다 보이는 작은 퍼즐이 아니라 **스크롤·줌이 필요한 큰 판**이다.
- 그룹이 **두 부류**로 나뉜다.
  - 희소형(04, 05, 10): 밀도 약 0.37, 45×45 안에 화살표 50~90개.
  - 밀집형(06, 07, 08, daily, thunderrush): 밀도 0.8~0.98, 빈칸이 거의 없다.
- 일일 레벨은 일반 레벨보다 **화살표 수가 약 1.5배, 라운드가 약 1.5배** 많다. 일일 레벨이 가장 어려운 콘텐츠다.
- 화살표 평균 길이는 9~13칸이고 꺾임은 2~5회다. 길이 2짜리 짧은 화살표가 상당수(그룹 07 기준 16%) 섞여 있다.

## 6. 난이도 구조

### 6.1 앱 안에서 확인된 단서 **[추정]** (메타데이터 클래스·필드 이름)

- `DefaultLevelDifficultyEvaluator`: 레벨 난이도를 점수로 매기는 평가기.
- `Bucketing`, `BuildBuckets`, `BucketCutoffs`, `BucketCapacity`, `BucketIdx`: 점수를 기준으로 레벨을 **난이도 버킷**에 나눈다.
- `BuildDifficultyChain`: 버킷을 이어 **난이도 순서(곡선)** 를 만든다.
- `DeterministicLevelBucketShuffle`: 같은 버킷 안에서는 **결정적 셔플**로 순서를 정한다(모든 유저가 같은 순서).
- `DiagonalLevelFrequency`: "각 난이도 버킷의 모양 아닌 레벨 N개마다 대각선 레벨을 하나씩 넣는다. 대각선 레벨은 반복된다"는 설명 문자열이 있다. 즉 **대각선 레벨은 N개마다 주기적으로 끼워 넣는 변주**다.
- `ArrowTypeCountMin`/`ArrowTypeCountMax`: 한 레벨에 **섞는 스타일 종류 수의 범위**로 보인다.
- `RollLevelConfig`, `LevelConfigs`: 서버나 설정에서 레벨 구성을 뽑는 흐름.

정리하면 이 게임은 **"생성 → 난이도 점수 매기기 → 버킷 분류 → 버킷 안에서 결정적 셔플 → 난이도 체인으로 연결"** 순서로 레벨 순서를 만든 것으로 보인다. 평가기의 실제 수식은 **[미확인]** 이다.

### 6.2 데이터로 측정한 난이도 지표 **[검증]**

규칙상 난이도를 결정하는 것은 화살표들의 **막힘 관계(의존 그래프)** 다. 화살표 A의 나가는 길에 B가 있으면 "A는 B가 먼저 나가야 한다"는 간선이 생긴다.

| 지표 | 정의 | 측정 결과 (그룹 07 / 08 / 10, 표본 300개) |
|---|---|---|
| 라운드 수 | 나갈 수 있는 걸 전부 뺀 뒤 다음 단계로 가는 횟수 | 31 / 29 / 19 (전체 평균) |
| 처음부터 나갈 수 있는 비율 | 처음에 막히지 않은 화살표 / 전체 | 0.13 / 0.10 / 0.22 |
| 최장 의존 사슬 | 의존 그래프에서 가장 긴 경로 | 32.9 / 27.7 / 19.0 |
| 화살표당 평균 막힘 수 | 나가는 길에 걸리는 서로 다른 화살표 수 | 4.4 / 4.3 / 3.1 |

- **처음부터 나갈 수 있는 화살표가 10~22%뿐**이다. 처음 화면에서 쉬워 보이는 선택지는 적고, 나머지는 연쇄로 풀린다.
- 라운드 수와 최장 사슬이 길수록 "순서를 계획해야 하는" 레벨이다. 화살표 수만 늘린다고 어려워지지는 않는다.
  - 예: 그룹 10은 화살표 57개·라운드 19, 그룹 07은 화살표 86개·라운드 31이다.
- 두 번째 숫자(프리셋)별 평균을 보면 단조 증가가 아니다. 예를 들어 `07-02`는 화살표 104개·라운드 36이고, `07-15`는 55개·19이며, `07-27`은 71개·28이다. **두 번째 숫자는 난이도 순위가 아니라 프리셋 ID**로 보는 게 맞다.

### 6.3 이 게임에서 난이도에 영향을 주는 요소

1. 화살표 수와 격자 크기
2. 밀도(빈칸이 많으면 막힘이 줄어 쉬워진다)
3. 평균 길이, 꺾임 수 (길고 많이 꺾일수록 걸리는 칸이 많아진다)
4. 의존 사슬 길이, 처음에 나갈 수 있는 비율
5. 대각선 사용 (방향이 8방향이라 눈으로 판단하기 어렵다)
6. 짧은 화살표(길이 2)의 비율 (쉬운 선택지가 섞이는 정도)
7. 스타일 조합 (Spaghetti·Loopy는 길게 얽혀 막힘이 많다고 추정)

## 7. 생성기에 가져갈 설계 근거

AI가 레벨을 만들면 너무 쉽거나 너무 어려워진다는 문제에 대한 근거다. 설계 결정은 아직 하지 않았고, 후보만 정리한다.

1. **풀이 가능성은 구조로 보장할 수 있다.**
   - 막힘 관계가 비순환이기만 하면 된다. 생성 후 그리디 솔버로 검증하면 끝난다.
   - 역방향 생성(빈 판에서 시작해 "마지막에 나가는 화살표부터" 채워 넣기)이 자연스러운 방법이다.
2. **난이도는 눈대중이 아니라 솔버로 잰 지표로 정한다.**
   - 라운드 수, 최장 사슬, 처음 나갈 수 있는 비율, 평균 막힘 수를 쓴다.
   - 원작도 평가기로 점수를 매기고 버킷으로 나눈 것으로 보이므로 같은 접근이다.
3. **"생성 후 걸러내기"가 핵심이다.**
   - 후보를 많이 만들고, 지표로 점수를 매기고, 목표 난이도 구간에 든 것만 채택한다.
   - AI가 만든 레벨이 극단으로 치우치는 문제를 이 필터가 막는다.
4. **난이도 곡선은 원작 데이터로 보정할 수 있다.**
   - 위 표가 기준선이다. 그룹별로 어떤 지표 범위를 쓰는지 알고 있으므로, 우리 곡선의 각 구간에 대응시킬 수 있다.
   - 원작 레벨을 그대로 쓰지는 않는다. 지표의 **분포**만 참고한다.
5. **스타일(경로 생성 알고리즘)을 모듈로 나눈다.**
   - 원작도 한 레벨 안에서 여러 스타일을 섞는다. 스타일 하나가 "조각 하나를 만드는 함수"가 되고, 레벨은 그 조합이다.
6. **변주는 주기적으로 끼워 넣는다.**
   - 대각선 레벨을 N개마다 넣는 것처럼, 단조로움을 깨는 장치로 쓴다.
7. **코어(규칙·생성기·솔버)와 스킨(그림)을 분리한다.**
   - 코어는 셀 좌표, 경로, 머리 방향, 막힘 관계만 다룬다.
   - 에셋 컨셉에 따라 코어 파라미터(꺾임 허용 여부, 길이 범위, 8방향 여부)가 달라진다.

## 8. 아직 모르는 것

- 난이도 평가기의 실제 수식과 버킷 경계값, 레벨 배치 순서 (코드 안에 있어 암호화로 막혀 있음)
- 플레이어가 실제로 어떤 순서로 레벨을 만나는지 (main 번들은 순서 없이 이름만 있음)
- `SpecialArrowId`, `_staticFlags`의 의미
- 하트 수, 부스터 종류와 효과, 힌트 동작 (이름만 확인, 수치는 서버 설정이거나 코드 안에 있을 가능성)
- 탭 동작의 세부 (길게 누르면 가이드라인을 보여 주는 것 같지만 `TapAndHold` 계열 클래스 이름 외에 근거가 없음)
- 막힌 화살표를 탭했을 때의 벌칙 (`BlockedAfterMistake`가 있어 일정 시간 막히는 것으로 보임)

## 9. 재현 방법

분석 스크립트는 스크래치패드에 있다(프로젝트에는 아직 넣지 않았다).

- 디코딩: UnityPy로 `Data/Raw/aa/iOS/levels-*.bundle`을 읽어 `MonoBehaviour`의 `Data`를 꺼낸다.
- 경로 복원: `CompactIndices`를 꼭짓점으로 보고 사이를 직선(대각선 포함)으로 채운다. 첫 값이 머리다.
- 풀이 가능 판정: 막히지 않은 화살표를 반복해서 제거하고, 남는 게 없으면 통과.
- 지표: 제거 반복 횟수(라운드), 의존 그래프의 최장 경로, 처음 나갈 수 있는 비율, 평균 막힘 수.
