# Parking Jam 3D 게임 로직 분석

분석 대상: `/Applications/ParkingJam3D.app` (iOS 앱, `com.uqxuwtxbbu.parkingjam`, v233.7.0, 빌드 2, 에셋 카탈로그 232.0.0)
목적: Arrows와 같은 계열의 퍼즐로서 규칙, 레벨 데이터, 난이도 구조를 파악해 레벨 생성기 설계의 근거로 쓴다.
Arrows 분석은 [arrows-game-analysis.md](arrows-game-analysis.md)를 참고한다.

근거 수준 표시: **[검증]** 레벨 데이터로 직접 확인 / **[추정]** 이름 등 간접 증거 / **[미확인]** 알 수 없음.

---

## 1. 분석 범위와 한계

- iOS 빌드이고, 실행 파일은 **FairPlay로 암호화**돼 있다(`cryptid 1`). 복호화하지 않았다. 그래서 이동 규칙, 생성기, 솔버의 **실제 코드는 읽지 못했다.**
- 읽은 것은 `global-metadata.dat`의 이름 문자열, 암호화되지 않은 Addressables 번들의 레벨 데이터, 프레임워크 목록이다.
- 레벨 데이터는 **1,748개**를 디코딩했다.
- 가장 큰 미해결 문제가 하나 있다. **차량이 어느 방향으로 움직이는지는 레벨 데이터에 없다.** 자세한 내용은 3절에 적었다.

## 3. 핵심 규칙

### 3.1 확인된 것 **[검증]**

- 판은 **정수 격자**다. 레벨은 `Min`/`Max` 좌표로 영역을 정한다.
- 차량은 **직사각형**이다. 전부 `2×3`, `2×4`, `2×5` 셀이고, 다른 모양은 없다(차량 약 4만 5천 대 전수 확인).
  - 비율은 `2×3`이 65%, `2×4`가 25%, `2×5`가 10%다.
- 장애물은 `WallData`(좌표, 종류, 방향)에 담긴다. 벽은 영역 둘레의 일부만 막고 **틈(출구)** 을 남긴다.
- 차량끼리 셀이 겹치는 레벨은 없다.
- 차량은 판을 **빠져나가면** 사라지는 것으로 보인다. 모든 차량을 없애면 클리어다 **[추정]** (`WinConditions`가 비어 있는 일반 레벨 기준).

### 3.2 미해결: 이동 방향 **[미확인]**

차량 데이터는 `Id`, `SortingId`(렌더링 순서로 보임), `HitBox`(셀 목록), `UnblockObject`, `Health`, `ColorId`뿐이다. **어느 쪽으로 가는지가 없다.**

기능이 없는 일반 레벨(할머니, 모디파이어, 움직이는 장애물이 없는 0-REG, 0-GRA 483개)로 가설을 검증했다.

| 가설 | 풀린 레벨 |
|---|---|
| 차량이 **긴 축**으로만 앞뒤 어느 쪽으로든 이동 | 409 / 483 (85%) |
| 차량이 **짧은 축**으로만 이동 | 19 / 483 (4%) |
| 차량이 **4방향** 어디로든 이동 | 479 / 483 (99%) |

- 긴 축만으로는 15%가 풀리지 않는다. 실제 게임에서 풀리는 레벨이 풀리지 않는 것으로 나오니, 이 규칙은 **불완전하다.**
- 4방향 가설이 더 많이 풀리는 건 가능한 이동이 더 많은 상위 규칙이라서 당연한 결과다. **이것만으로 4방향이 맞다고 할 수 없다.**
- 가능한 설명:
  1. 방향이 차량 프리팹이나 런타임 코드에서 정해진다(데이터에 없음).
  2. 차량이 방향을 바꿀 수 있다(회전이나 후진).
  3. 출구 규칙이 내 가정(영역 밖으로 나가면 탈출)과 다르다.
- 풀려면 앱을 실제로 플레이해서 차를 탭했을 때 어떻게 움직이는지 확인하거나, 코드를 읽어야 한다. 이 문서의 이후 내용은 이 불확실성을 전제로 한다.

### 3.3 Arrows와 규칙 비교

| 항목 | Arrows | Parking Jam 3D |
|---|---|---|
| 조각 모양 | 꺾이는 경로(길이 가변) | 2×N 직사각형(3~5칸) |
| 막힘 판정 | 머리 방향 직선 위에 다른 조각 | 이동 경로 위의 차량·벽 |
| 방향 정보 | 데이터에 있음(첫 값이 머리) | **데이터에 없음** |
| 풀이 판정 | 그리디 한 번으로 충분 | 방향 규칙에 따라 같을 가능성 |
| 출구 | 격자 밖 | 벽 틈 / 영역 밖 |

두 게임은 "막힌 조각을 순서대로 빼내는" 같은 계열이다. Arrows는 조각의 모양이 자유롭고, Parking Jam은 조각이 단순하지만 **판 위에 특수 오브젝트가 많다.**

## 4. 레벨 데이터 포맷 **[검증]**

레벨 하나는 ScriptableObject 하나다.

```
Min, Max           : 영역 좌표
CarData[]          : Id, SortingId, HitBox[](셀), UnblockObject, Health, ColorId
WallData[]         : Position, Type, Orientation
MovingObstaclePath : 움직이는 장애물 경로 (좌표 목록)
Grannies[]         : 할머니(보행자) 경로
Helipads[]         : 헬리패드 (Position, Size)
Manholes[]         : 맨홀 (Position, Size, 애니메이션 주기)
ConstructionSites[]: 공사장 (Position, Size)
KeyLockData        : 열쇠를 가진 차(KeyCarrierCarIds), 잠금 (KeyId, LockType, EntityId)
LimitedMoves       : 이동 횟수 제한 (0이면 무제한)
AdditionalLives    : 추가 목숨
ChallengeTimeMultiplier, HardChallengeTime, UnblockTimer : 시간 관련
FilledSquares      : 차량이 차지한 셀 수 (자동 계산 값으로 보임)
LevelModifiers[], WinConditions[] : 다형성 객체 (references 영역)
```

- `FilledSquares`는 차량 셀 수의 합으로 보이며, 레벨 크기에 대한 표시 값이다.
- `LevelModifiers`/`WinConditions`는 클래스 이름이 붙은 객체로 직렬화된다. 예: `CarSpawningLevelModifier`(스폰 간격, 차 수, 후보 색), `FreeColoredCarsWinCondition`.
- 벽 `Type`은 값이 매우 다양하다(0, 1, 2, 3, ..., 29). 장식이나 다른 종류의 장애물을 같이 담는 것으로 보인다 **[추정]**. `Orientation`은 0~4로 방향이다.

## 5. 레벨 종류와 통계 **[검증]**

|---|---|---|---|---|
| `Challenges-GRA` | 538 | 32×20 | **55** | 대형. 제한 이동 100%, 움직이는 장애물 98% |
| `0-REG` | 498 | 14×12 | 9 | 일반 레벨 |
| `0-GRA` | 179 | 14×12 | 9 | 일반 레벨(할머니 일부) |

| `car_spawning_v1~3` | 130 | 13×12 | 8 | 차량이 **계속 새로 나오는** 모드. 모디파이어와 승리 조건 포함 |
| `AdvMode_*` (Space/Viking/Beach/Jungle) | 180 | 17×15 | 19 | **어드벤처 모드**. 헬리패드, 맨홀, 열쇠 등 특수 오브젝트 |

### 난이도 지표 (일반 레벨)

- **일반 레벨은 작다.** 차량 약 9대에 격자 14×12다. 한 번에 빼낼 수 있는 차를 모두 빼는 반복 횟수(라운드)는 **약 3**이다(긴 축 가설 기준, 풀린 레벨만).
- Arrows의 같은 지표는 19~47이었다. Parking Jam의 일반 레벨은 **풀이 깊이가 훨씬 얕다.**
- 일반 레벨은 인덱스가 올라가도 차량 수가 거의 늘지 않는다. 0~50번 7.6대, 50~100번 10.4대, 이후 8~10대로 **평평하다.**
  - 난이도를 올리는 장치가 **차량 수가 아니라 제한 이동 횟수, 특수 오브젝트, 모드 변주**에 있다는 뜻이다.
- 제한 이동(`LimitedMoves`)이 걸린 레벨 비율은 0-REG 28%, 0-GRA 35%이고, 챌린지는 100%다. 제한 값의 평균은 인덱스 0~100과 350 이후 구간에서 높고(5~12), 150~300 구간에서는 0이다.
- 챌린지는 일반 레벨의 약 6배 규모(차량 55대)이고 라운드는 약 11~14다. Arrows의 일일 레벨(화살표 129개, 라운드 47)과 비슷한 위치의 "하드" 콘텐츠다.

### 특수 오브젝트 (어드벤처, 챌린지 후속 중심)

| 오브젝트 | 데이터 | 효과 **[추정]** |
|---|---|---|
| 할머니 | 경로(좌표 목록) | 경로를 오가며 지나가는 보행자. 차가 부딪치면 실패 |
| 움직이는 장애물 | 경로 | 주기적으로 길을 막음. 챌린지에 대부분 있음 |
| 헬리패드 | 위치, 크기 7×7 | 차량을 들어 올려 옮김 |
| 맨홀 | 위치, 크기, 애니메이션 주기 | 주기적으로 열리고 닫힘 |
| 공사장 | 위치, 크기 | 통과 불가 구역 |
| 열쇠·잠금 | 열쇠를 가진 차, 잠금 대상 | 열쇠 차를 먼저 빼야 잠긴 차를 뺄 수 있음 |
| 체력 차량 | `Health` | 여러 번 부딪쳐야 사라짐 (`0-DAM` 접두사와 일치) |
| 언블록 | `UnblockObject`, `UnblockTimer` | 시간이 지나면 풀리는 구조물 |

이름 기반 추정이다. 효과의 정확한 동작은 코드를 못 읽어 확인하지 못했다.

## 6. 게임 모드 구조 **[추정]**

번들 이름과 클래스 이름으로 보이는 모드: 일반(0-REG/GRA/DAM), 챌린지, 어드벤처(테마별 45레벨 × 4), 엔드리스, 타임트라이얼, 언블록, **차량 스폰(car spawning)**, 일일 그림·레이스.

메타 요소: 차량 수집·제작(`CarBuilding`), 스킨·트레일(수십 종), 환경(공항, 해변, 중세 등 수십 종), 아이들 게임(`TapToBuild`, 섬과 건물), 리더보드, 목숨, 이벤트(시즌 한정 차량과 환경), 상점·IAP.

핵심 퍼즐은 같은데 **포장과 모드가 매우 많은 게임**이다. 퍼즐 자체가 단순하기 때문에 변주와 메타로 콘텐츠량을 늘린 구조다.

## 7. 내장된 생성기·솔버 **[추정]**

메타데이터에 다음 이름이 있다.

- `LevelGeneratorService`, `GeneratorConfig`, `LevelGeneratorCarType`, `LevelSizeRandomizationDelta`
- `LevelSolver`, `LevelSolverResult`
- `LevelEditorGrid`, `LevelEditorLimitedMoves`, `LevelEditorValidRemovedEventSystem`
- `LevelDataCsvColumnService`, `LevelImportConfig`

해석:

- 원작에는 **레벨 에디터와 생성기, 솔버가 이미 있다.** 에디터에서 만든 레벨이나 생성된 레벨을 솔버로 검증하는 흐름으로 보인다.
- 생성기는 크기를 **무작위로 흔드는** 파라미터(`LevelSizeRandomizationDelta`)를 쓴다.
- 솔버의 결과(`LevelSolverResult`)가 `LimitedMoves` 같은 값을 정하는 데 쓰일 가능성이 있다. 최소 이동 횟수에 여유를 더해 제한을 거는 방식이다 **[추정]**.
- 생성된 레벨(`Generated_TTR_*`)은 20개뿐이고 나머지는 사람이 만든 것으로 보인다. 즉 **핵심 레벨은 수작업 디자인**이다.

## 8. 두 게임에서 얻는 설계 시사점

1. **둘 다 "막힌 조각 빼내기" 구조**라서 코어(격자, 조각, 막힘 관계, 솔버)를 공유할 수 있다.
2. **난이도 조절 수단이 다르다.**
   - Arrows: 의존 사슬을 길게 만들어(라운드 수) 난이도를 올린다.
   - Parking Jam: 판은 작게 두고 **제한 이동 횟수와 특수 오브젝트**로 난이도를 올린다.
   - 생성기에는 "구조 난이도"와 "제약 난이도(이동 제한)"를 **따로 조절하는 축**이 필요하다.
3. **솔버로 최소 이동 횟수를 구하면 제한 이동을 자동으로 정할 수 있다.** 풀이 경로가 여러 개일 때 "최적해보다 몇 번 여유를 주는가"가 체감 난이도다.
4. **특수 오브젝트는 모듈로 분리한다.** 각 오브젝트가 규칙을 하나씩 추가하는 구조라, 처음에는 코어만 만들고 오브젝트를 하나씩 얹는 순서가 좋다.
5. **핵심 레벨은 수작업이 많다.** AI 생성이 너무 쉽거나 어려워지는 문제를 막으려면, 생성 후 **솔버 지표로 걸러내는 단계**가 필수다. 두 게임 모두 같은 결론이다.
6. **이동 방향 규칙은 우리 게임에서 직접 정하면 된다.** 원작 규칙이 불명확해도 생성기는 우리가 정한 규칙(조각마다 방향을 데이터에 명시)으로 만들 수 있다. Arrows 방식처럼 방향을 데이터에 포함하는 쪽이 생성과 검증이 쉽다.

## 9. 아직 모르는 것

- 차량의 이동 방향 규칙과 출구 판정 (3.2절)
- 벽 `Type`(0~29) 각각의 의미
- 특수 오브젝트의 정확한 동작
- 레벨 배치 순서, 난이도 곡선의 실제 구성 (인덱스는 제작용 ID로 보이며 플레이 순서가 아님)
- `LimitedMoves`를 정하는 규칙
- 목숨, 보상, 광고 노출 시점 등 메타 수치

## 10. 재현 방법

분석 스크립트는 스크래치패드에 있다(프로젝트에는 넣지 않았다).

- `Data/Raw/aa/iOS/defaultlocalgroup_assets_all_*.bundle`을 UnityPy로 읽으면 `CarData`와 `Min`이 있는 MonoBehaviour가 레벨 데이터다.
- 이동 가설 시험: 차량의 `HitBox`를 방향별로 평행 이동하며 벽, 남은 차량과 충돌하는지 보고, 영역 밖으로 나가면 제거한다. 제거할 수 있는 차가 없을 때까지 반복해 풀이 가능 여부를 본다.
