진단만 했습니다. 기존 렌더러, 게임, 승인 PNG는 바꾸지 않았습니다.

- **장면:** 실제 게임의 카메라와 판을 그대로 씁니다(`?demo=sheet`, 원근 카메라 시야각 32°, 58°). 판의 위·가운데·아래 줄 × 0/90/180/270°, 390×844.
- **도구:** `diag/cardModes.ts`(A/B/C 전환), `diag/vite.diag.config.ts`(포트 5431), `diag/measure.mjs`, `diag/analyse.py`. 결과는 `out-diag/`(3줄 장면), `out-diag-1row/`(높이용 1줄 장면)에 있습니다.
- **측정 방법:** 실제 카메라로 투영한 좌표를 쓰고, 카드가 있는 화면과 없는 화면을 비교해 실제로 보이는 픽셀을 구했습니다. 단위는 그 위치의 칸 폭입니다.
- **A/B/C:** 같은 PNG와 같은 매니페스트를 씁니다. 배치 방식만 다릅니다.
  - A 현재: 바닥 y=0에 기준점, 그림 아래쪽 높이만큼 카메라 쪽으로 당기고 크기를 다시 맞춤
  - B 월드 기준: 판 윗면(y=0.1)에 기준점, 당기지 않음
  - C 화면 기준: 판 윗면 바닥점의 화면 위치에 기준점을 정확히 맞추고, 깊이는 블록 중심

## 판단

- **렌더러 문제 (A에서만 생김, C로 해결):** 투명 여백에 따라 달라지는 카드 당김, 기준점이 판 윗면 아래에 있음, 원근에서 좌우 어긋남. → 발 묻힘, 깊이 순서 오류, 0.16칸 어긋남.
- **PNG 문제 (렌더러로는 못 고침):**
  - 배치 2·3의 0°·180° 정면 그림은 시점이 게임 카메라와 다름. (정정: 악어 0° 그림은 기하학적으로 더 길지 않습니다. 높이/폭 1.1~1.4로 다른 종의 1.0~1.2와 비슷합니다. 악어가 2.39칸으로 보이는 것은 offset이 없기 때문입니다. 악어가 한 몸으로 읽히는 것은 윗면 무늬를 그린 방식 때문이라는 시각 판단이고, 수치로 측정한 사실은 아닙니다.)
  - 병아리 3/4 그림, 악어 부품 높이 차이, 2칸 머리 90°의 다리 없음.
- **아직 검증하지 않은 것:** C 방식에서 카드와 3D 장애물(울타리·상자 등) 사이의 깊이. 이번에는 카드끼리의 순서만 측정했습니다. 회전 중 C의 동작도 아직 보지 않았습니다.

## 가장 적은 변경

`spriteCards.ts` 한 파일의 카드 배치 부분(약 30줄)을 C 방식으로 바꾸는 것입니다. 판 윗면 기준점, 화면 투영 정렬, 블록 중심 깊이를 적용합니다.
- **해결되는 것:** 발 묻힘, 깊이 순서 오류, 좌우 어긋남
- **영향:** 기존 9종과 배치 3 모두 바뀝니다. 발이 약 0.06칸 올라가고, 판 가장자리에서 좌우가 최대 0.16칸 이동합니다.
- **남는 것:** 0°·180° 압축, 악어 단차, 병아리 그림은 그대로입니다. 그림을 다시 만들거나 보정 정책을 정해야 합니다.


## 2차 진단 (2026-11-02): 터치, 장애물, 회전, offset, 병아리

### 터치 (실측, `diag/touch.mjs`, 4개 장면 × 4px 격자)

- 게임은 카드 평면 전체에 광선을 쏴서 동물을 고릅니다(`main.ts animalAt`). 그런데 카드 평면은 대부분 투명합니다.

| | 동물이 보이는 점 중 다른 동물이 선택됨 | 그중 투명 부분 때문 | 빈 바닥을 눌렀는데 동물이 선택됨 |
|---|---|---|---|
| A | 19~36% (붐비는 판 19%, 레벨 60은 36%) | 100% | 2,510~3,700점 |
| C | 16~32% | 100% | 2,478~3,597점 |
| A·C + 투명 부분 제외 판정 | **0%** | — | 712~949점 (모두 게임의 0.75칸 바닥 판정 규칙이고, 3D와 같은 동작) |

- 실제 터치로도 재현했습니다. 다른 동물이 보이는 지점을 누르면 아무도 출발하지 않거나(16회), 다른 동물이 출발했습니다(레벨 20의 A, 4회).
- 대조군으로, 판정이 맞는 지점을 누른 탭은 16회 중 15회 성공했습니다.
- **원인:** 좌표 변환이나 점유 칸 문제가 아닙니다. 카드의 투명 부분이 탭을 가로챕니다. 렌더러 안에서 카드 메쉬의 `raycast`를 투명 부분 제외로 바꾸면 해결되고, 게임 코드는 바꿀 필요가 없습니다.

### 3D 장애물과 탈출 (실측 + 육안)

- 장애물이 가장 많은 레벨 47·49·51에서 비교했습니다. 카드가 앞줄 장애물 위에 그려지거나, 뒷줄 장애물이 카드를 가리는 경우는 A·C 모두 0건이었습니다. 다만 카드와 장애물이 같은 광선에 걸린 경우가 3~13개뿐이라 표본이 적습니다. 육안으로 본 A·C 화면도 같습니다(`diag-obstacles-AC.png`).
- 출구 축소 애니메이션도 A·C가 같습니다(`diag-exit-AC.png`).

### 회전 (실측, 위치 고정 캡처)

- 2칸 회전 4건: 프레임 간 변화 최대치가 A와 C 모두 중앙값의 1.5~2.8배이고, 같은 프레임에서 나타납니다. C가 회전을 나쁘게 만들지 않습니다.
- 3칸 4종 × 0°→90°, 180°→270° × offset 배율 1·0.5·0: 최대치 1.1~1.7배이고, 2배를 넘는 프레임은 0개입니다(`diag-3cell-turn-offsets.png`).

## 3. 방식별 타당성 평가 (2026-11-02)

평가 기준은 세 가지입니다. ① 점유 가독성 ② 연결 안정성 ③ 일반화(종별 예외 보정 없이 공통 렌더러로 관리할 수 있는가).

| | 부품별 PNG 카드 + C 배치 | 2D 메시 변형 / 스켈레톤 | Classic 3D |
|---|---|---|---|
| ① 점유 | offset ×0이면 길이는 맞음(3칸 2.5~2.7). 하지만 0°·180° 그림이 정면 시점이라 블록을 쌓은 모양. 그림을 악어처럼 다시 그려야 한 몸으로 읽힘 | 리본 메시는 경로를 따라 이어지므로 원리상 맞음. 다만 58° 카메라에서는 등(위) 텍스처가 필요 | 맞음 (실측 2칸 2.0, 3칸 2.5~2.8). 형상 그대로라 방향과 관계없음 |
| ② 연결 | 옆모습 틈 0, 회전 위치 튐 0. 다만 4방향 그림이 바뀔 때 실루엣이 변함(알려진 한계). 악어 단차 0.12칸, 2칸 머리 90°의 다리 없음은 그림 문제 | 회전 중 연속(구조상 이음매 없음). 머리·꼬리를 카드로 그리면 그 이음부에는 카드 문제가 그대로 남음 | 연속. 블록이 그대로 회전함 |

| 남는 한계 | 방향 전환 시 실루엣 변화. 그림 생성의 일관성(배치 2·3에서 방향 반대, 다리 누락, 높이 차이, 검은 배경이 반복) | 새 그림 파이프라인과 새 렌더러. 스켈레톤(Spine 등)은 리깅된 그림이 필요해 ChatGPT 생성 방식과 맞지 않음 | 콘셉트 점토 화풍과의 차이(원래 2.5D를 시작한 이유) |
| 추가 작업 | 렌더러 수정 1회 + 그림 약 25장 재제작 + 검증 | 렌더러 개발 + 그림 규격 새로 정의 + 전 종 재제작 | 없음 (화풍 개선은 별도 과제) |
